## 3. Errata — where the review is wrong or stale

These matter: they keep workers from "fixing" things that aren't broken.

1. **Search compression** ("no totals, prompt-detection is the only guard") — largely wrong. The grep path emits an aggregate omitted count plus per-file `N matches, M shown` lines (`:428-432`), keeps every SIGNAL/relevance-token match, retains `path:line` on every kept line, and has six other guards besides `requestsEnumeration` (`HUSH_GREP=off`, 4KB floor, context-flag and output-mode gates, common-token filter, not-smaller guard). The real gap is only: nothing **persists** the omitted matches (recovery = re-run advice).
2. **Disable and state writes** — all seven hooks' file writes are gated; the only leaks are the nudge hook's context injection and the style forcing (§2 B1). Entry 162's file list was smarter than the review's blanket wording.
3. **"Not-smaller rejected"** exists today at six sites (MCP `:562`, exec `:601-604`, sidecar `:857`, delta `:1019`, grep `:433`, global backstop `:1352`) — scattered, not missing. 164's manifest centralizes; it does not introduce the concept.
4. **Range-read invariant** (contract invariant 4) is today **violated** on log/generated paths: `isRangeRead` (`:1239`) exempts only the delta, not compression — probe: `offset:100,limit:200` on a log path is rewritten byte-identically to the no-range control. The contract states it as a target; no roadmap entry names it. Folded into 163 (§4).
5. **Stale style facts:** Anchor was already deleted at HEAD (`4c0d45a`); stock is already described as tired/ADHD-reader-first. Residue the review missed in the other direction: `README.md:157` still says "six shipped presets" (four ship); `styles/README.md:3,7` "five voices" vs "writes a fifth" collide.
6. **Two roadmap "what" clauses are already shipped behavior:** 166's "keep command execution native by default" (wrapping is already opt-in) and 165's "preserve original output when recovery storage fails" (`maybeSidecar` returns null on any throw and the inline path proceeds). Workers should treat both as conformance tests to add, not code to write.
7. **Precompact cap** is not a raw first-20 directory slice: it session-filters first (`precompact-summary.js:60-64`), then takes an unsorted 20 with no "N more" marker — silent drop confirmed by probe (26 live, 20 listed).
8. **Marketplace/plugin description** "measured on real multi-turn coding sessions" — real headless sessions, yes; but fixtures are synthetic mini-repos and 1/15 tasks is multi-turn. Belongs to 173's rewrite scope.

## 8. Operating methodology (user-set, 2026-07-28 — supersedes §6/§7 where they differ)

1. **One wave per orchestrator turn.** Finish the wave, report, stop. The user's next "go" starts the next wave.
2. **The orchestrator never writes code.** Coders are Opus 5 `roadmap-implementer` dispatches (model override `opus`), serial, one entry each, §6 protocol: branch inside `hush/`, orchestrator reviews the diff, squash to one commit per entry, suite green env-clean (`HUSH_DEBUG` cleared, `node --test "tests/*.test.js"`).
3. **Wave-end adversarial review, before reporting.** Dispatch a FRESH Fable agent (model `fable`, user-set 2026-07-28; never an implementing agent) over the wave's full diff range in `hush/`, the wave entries' texts, and their §4 notes. Its contract, verbatim: "Return: a verdict (APPROVE or REQUEST-CHANGES) plus a list of confirmed defects (with the repro input and actual vs expected output) and any minor style notes. Only report defects you actually reproduced." The reviewer must execute probes (fnm init for node; clear `HUSH_DEBUG`; TEMP redirected to scratch; no repo writes). For docs-only changes, "reproduced" = the quoted text against the spec. Defects in code the wave did not touch are reported separately as roadmap candidates — they never block the wave.
4. **REQUEST-CHANGES loop, same turn.** Orchestrator dispatches an Opus fix (a small separate `fix:` commit referencing the entry), re-reviews, repeats until APPROVE.
5. **Acceptance.** Wave entries close to `awaiting_acceptance` with their commit shas. The user's next "go" accepts the prior wave (orchestrator then flips those entries to `done`) unless the go message objects.
6. **Releases.** Cut at a wave boundary only when the user's go says so; never push without an explicit push instruction. Check parent-repo status first — the foreman stream shares `ROADMAP.jsonl` and `marketplace.json`.
7. **Context reset between waves.** All program state lives in this doc (§9 wave log), ROADMAP.jsonl, and auto-memory — nothing load-bearing may exist only in chat. After a wave is accepted the orchestrator hands the user a kickoff prompt; the user clears/compacts the conversation and pastes it. Template: `Go: hush remediation Wave <X>. Read docs/hush/research/hush-groundtruth-and-delivery-strategy-2026-07-28.md end to end — §8 is the operating methodology, follow it exactly. Run Wave <X> per §6, then stop.`
8. **Mid-wave surprises** that exceed an entry's §4 scope: pause that entry, finish the rest, surface it in the wave report.
