---
id: 106
title: Give invariants their own block and keep the file surface a constraint line
date: 2026-07-25
---

## Decision
Of the three new optional per-task fields, only the invariants get their own XML
block, `<invariants>`. The expected file surface is one more bullet under
`task_rules`' existing `Constraints:` heading, and the test-first ordering is a
bracketed instruction inside the existing verification block. Registering the new
`<invariants>` placeholder in `PLACEHOLDER_FRAGMENTS` is part of adding the block,
not a change to what the gate does: `checkPrompt` has no block whitelist, so the
fragment list is the registry of placeholders that must not survive assembly, and
an unregistered placeholder would ship into handoffs unflagged.

## Context
The entry asked for three fields, and the obvious symmetric move is three new
blocks. Two of them have an existing home that already carries their meaning:
`Constraints:` is where "files NOT to modify" already lives, so the expected file
surface is the same kind of statement, and the verification block is where an
ordering over checks belongs. Only the invariants are a new kind of content — a
statement that must stay true across the change, independent of any command.

## Alternatives rejected
- Three separate XML blocks — two of them would restate what `Constraints:` and
  the verification block already frame, and every extra block is one more thing
  every crafting path has to decide about.
- Fold invariants into `Constraints:` too — a constraint bounds what the session
  may do; an invariant is what must remain true afterward, and collapsing them
  loses exactly the distinction the entry exists to create.
- Ask the user for the file surface and the test-first ordering at craft time —
  both are inferable (`touches` / Call 2 Q3 for the surface, the task's own
  failure mode for the ordering), and `foreman:roadmap`'s pick branch is
  explicitly not a second interview.

## Consequences
All three fields are optional and their absence is silent — no gate error, no
warning, and the checklist item asks only that a present field be well-formed.
Anything added to the template's XML fence as a bracketed placeholder must be
registered in `PLACEHOLDER_FRAGMENTS`, or the drift-pin test in
`check_prompt.test.js` fails — which is the intended guard, not an obstacle.
