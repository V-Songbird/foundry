id: 104
title: State the order once in a fixed plan block, and keep the entry paragraph outside it
date: 2026-07-26
---

## Decision
The handoff prompt gains a fixed `<plan>` block at the end of the template,
carrying three numbered steps — read the cited files, make the change, run the
checks — plus one rider sentence about the roadmap entry paragraph. The block is
whole-cloth fixed text with no substitutions, so `readCanonical` parses it out of
the template's xml fence alongside `truth_grounding` and `scope_discipline`, and
`checkPrompt` compares it verbatim. That is the cheapest possible enforcement:
one `extractBlock` call and one `norm` comparison, no sentence constant, no
fixture that drifts. The plan deliberately does NOT absorb the entry's open and
close steps. Those stay in the entry paragraph, and the plan's rider names their
position relative to steps 1 and 3 instead. Exactly one duplicate is deleted as
part of this: `task_rules`' default read-first bullet, in both the template and
`skills/roadmap/SKILL.md`, since plan step 1 now states it once for every task.

## Context
An assembled prompt stated its sequence in four places at once, and none of them
claimed to be the whole order, so the session had to assemble the order itself
before it could start on the problem. The constraint that shaped the answer is
the task-split rule: `hooks/task-completed.js` gates every completing task whose
description names an entry, so the entry paragraph rides the LAST task row only.
A plan block that swallowed the open and close steps would inherit that same
last-row-only restriction, and every earlier row would then carry a plan missing
its own ending — strictly worse than the four-places status quo it replaced.
Splitting the difference (universal steps in the plan, entry steps referenced by
position) lets the plan ride every row unchanged.

## Alternatives rejected
- Plan absorbs the entry's open/close steps — inherits the last-row-only
  restriction and leaves non-final rows with a truncated plan.
- Plan enforced by a sentence constant plus an `includes` check, like the
  guardrails under entry 103 — those two live inside assembler-filled sections
  and had no other option; this block is wholly fixed, so verbatim comparison is
  both stronger and less code.
- Delete the analyze and implement bullets too, since the plan covers step 2 —
  those bullets are the task's content, not its ordering; only the read-first
  bullet was pure procedure.
- Leave `task_rules`' read-first bullet in place — it is the one instruction the
  plan restates word for word, and a consolidation that deduplicates nothing
  fails the governing principle from the same docs review: reasoning is removed
  only by replacing it with a fact the session no longer derives.

## Consequences
`plan` and `invariants` are now in `render-sections.js`'s `RESERVED_TAGS`, so a
project's `customSections` cannot shadow either — `invariants` had been missed
when entry 106 added it, and was fixed here on the user's explicit approval to
step outside this entry's declared file surface. Never write a template-owned tag
in angle brackets inside the template's own prose: an instruction bracket in
`task_rules` mentioned the plan tag that way, and `extractBlock`'s non-greedy
regex matched that mention instead of the real block, so the parsed "plan" was
3246 characters of the rest of the template and eleven placeholder errors fired
at once. The rule is now: refer to a block as "the plan block", never as the
literal tag. Anything future work adds to the fixed sequence belongs in the plan
block, not in a fifth place.

## Findings
The four-place sequence was: the entry paragraph's open step, `task_rules`'
read/analyze/implement bullets, the `Verification (REQUIRED):` block, and the
entry paragraph's close step. Only the first bullet was a true duplicate; the
rest were single statements that merely lacked a stated order, which is why this
entry trims one bullet rather than a third of the prompt. The "roughly a third"
figure in the entry's notes is credited to this change *together with* a separate
bookkeeping move, and this half alone does not approach it.
