---
id: 119
title: Remove checkpoints.push instead of constraining it
date: 2026-07-26
---

## Decision
The `checkpoints.push` key is removed from `.foreman/config.json`, not deprecated and not
gated. Checkpoint commits made by a task-split run always stay local. The only step in the
whole checkpointing protocol that reaches a remote is `onFinish`'s `Open a PR` option,
which pushes a finished branch on purpose. `prompt-template.md`'s config-resolution bullet
now names three keys — `branch`, `onFinish`, `baseBranch` — and carries an explicit
never-add-`push` rule pinned by a drift test in `check_prompt.test.js`.

## Context
`push` fought the default ending. `onFinish` defaults to `"ask"`, whose recommended
answer squashes the checkpoint branch onto the base and deletes it, so every pushed
`task <n>/<total>:` commit was history the next step rewrote, and the deleted local branch
left an orphan on the remote that nothing cleaned up. With `branch` set to `false` the
same setting was worse still: checkpoints land in place on whatever branch the session
already occupies, so `push` shipped work-in-progress commits straight to a possibly
shared branch. No configuration of the remaining keys made `push` safe under the
default ending.

## Alternatives rejected
- Keep `push` but reject `true` unless `onFinish` is `keep` or `pr` — a setting valid only
  in two of five endings is a trap with a validator attached, and the resolution step has
  no user-visible warning channel to explain the rejection.
- Keep it and document the interaction — the documented advice would be "don't set this",
  which is the removal with extra reading.
- Keep it for crash protection — the commits themselves are the protection; they survive
  on disk without a remote, and a run that wants a remote copy has `Open a PR`.

## Consequences
A project that set `checkpoints.push` sees the key silently ignored; the README and
changelog are where that is announced. The clipboard checkpoint embed bakes one fewer
value into the pasted prompt. Anyone re-adding a push step to the checkpointing protocol
has to defeat a named drift test, which is the intended friction. Never reintroduce the
key without also changing `onFinish`'s default away from a history-rewriting ending.

## Findings
`onFinish` and `branch` do not conflict: the ending applies only to a branch the run
created itself, so `branch: false` skips `onFinish` entirely and a `"squash"` value is
inert there. That was already true in the protocol but stated nowhere a user would look,
so the README settings row now says it.
