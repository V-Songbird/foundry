**Superseded 2026-08-01 (entry 146, foreman 1.0 close):** the Effort fit / Model fit notes were deleted with the whole model-advice surface — `prompt-template.md` carries neither, and `model-fit.md` no longer exists. Historical only.

## Decision — the choice, named, in one paragraph

Effort becomes the second half of the existing model recommendation, not a
new question and not a new config key. `prompt-template.md` gains an
**Effort fit** note directly under **Model fit**, keyed on verification
cost: a runnable check already in `task_rules` argues low/medium with
escalation on failure, a silent failure mode argues high, and no
verification at all argues max. Both skills point at that note and state
the recommendation in one line of the delivery message — the setting plus
the verification-cost reason behind it — on every destination, including
`Execute here`, where it applies to the crafting session's own effort. The
recommendation is never asked as a question and never dispatched, because
there is nothing to wire an answer to: the `Agent` tool takes no effort
argument. The operator acting on the stated line is the whole mechanism.

## Context — the constraint that forced it

Model fit (entry 053) already recommends a model and lets the operator
confirm it, because the model IS a dispatch value on the `Agent` path.
Effort has no such value — it is a per-call parameter of the harness, not
of the tool Foreman calls, so a question would collect an answer nothing
could consume. At the same time effort matters more than usual here: the
assembled prompt's closing paragraph tells the destination to think rather
than narrate, which makes reasoning budget the only deliberation channel
the prompt leaves open.

## Alternatives rejected — one line each: the option and the single reason it lost

- A `targetEffort` key in `.foreman/config.json` — effort is per-call, so a
  project-level pin would be wrong for most tasks in the project.
- A fifth question (or extra options in Call 6) asking the operator to pick
  an effort — collects an answer with no consumer, and spends one of
  `AskUserQuestion`'s four option slots.
- Renaming the "Model fit" heading to "Model and effort fit" — both skills
  and the checklist cite the note by its current name, so a sibling
  **Effort fit** paragraph extends it without breaking those references.
- Skipping the recommendation on `Execute here` (mirroring Call 6's skip) —
  the model choice genuinely doesn't exist there, but the effort choice
  does; it is this session's own setting.
- A `check-prompt.js` rule for effort — effort guidance is craft-time prose
  outside the xml fence, so the checker has nothing to inspect.

## Consequences — what future work is committed to, plus any never-touch warning

The recommendation lives in three places that drift apart easily, so two
drift pins in `check_prompt.test.js` hold them together: one asserts the
template still carries `**Effort fit**`, the no-`targetEffort` sentence, the
never-dispatched sentence, and all three effort branches; the other asserts
both SKILL.md files still cite the `"Effort fit" note` and the
never-dispatched rule. The second pin matches with a whitespace-tolerant
regex because the roadmap skill's prose wraps mid-sentence — a plain
`includes` on that phrase fails there.

Never bake the effort reasoning into the assembled prompt. It is the same
rule the Haiku caution already follows: the target model does not see a
description of its own expected failure modes.

## Findings

Entry 102 ("record which model and effort executed each entry") is the
natural follow-on and stays untouched here — this entry recommends an
effort, it does not record what actually ran.
