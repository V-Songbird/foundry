title: Carry the three craft-time preflight facts on the existing resolver call
date: 2026-07-26
---

## Decision
The verification-command check, the reference-implementation lookup, and the file-age
report all ride `resolve-symbols.js` rather than becoming their own scripts or their own
craft-time steps. Each is an additive output field on the call the crafting session
already makes: `verification` when a `verify` command is supplied, `references` always,
and a `lastChanged` key per file. Every one of them fails soft — an unresolvable command,
an absent git repository, and a truncated scan are all reported in `warnings` or by an
absent field, never by a non-zero exit. The reference scan is a bounded tree walk capped
at `WALK_LIMIT` files, skipping `node_modules`, build output, and dotted directories.

## Context
The crafting session pays one round trip per craft-time script. Three separate scripts
would triple that cost for facts that share the same input — the entry's `touches` and
its `what` — and the calling skill would have to remember three call sites instead of
one. The cap on the walk exists because that walk is overhead paid on every single
prompt: it must not grow with the repository.

## Alternatives rejected
- Three separate scripts — triples the craft-time round trips for one shared input.
- `git grep` or `rg` for the reference scan — neither is guaranteed on PATH, and the
  existing header comment already records that as the reason this script has no
  dependencies.
- An unbounded walk — craft-time cost would scale with the repo, silently, on every
  prompt.
- Failing the call on an unresolvable verification command — craft time reports facts;
  blocking assembly on one would make a soft signal into a gate the operator cannot
  route around.

## Consequences
Any future craft-time fact derived from `touches` or `what` belongs on this same call,
not on a new script. `resolves` answers only "does this entry point exist here", never
"does the command pass" — widening it into an execution check would run project commands
at craft time, which this call must never do. A leading `cd <dir> &&` is parsed because
that is how a submodule's suite is named from the repo root; any further shell grammar is
out of scope, and an unparsed prefix degrades to `resolves: false`, which is a visible
warning rather than a wrong answer.
