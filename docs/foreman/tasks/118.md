id: 118
title: Default requireVerification to true
date: 2026-07-26
---

## Decision
`requireVerification` is on unless a project sets it to exactly `false`. `readConfig` in
`hooks/post-commit.js` now reads it the same way it already reads `discoverySuggestions`
— present-and-false opts out, anything else is on — and the catch branch that handles an
unreadable config returns the same on value. `foreman:init`'s Q3 leads with the
confirm-first option and marks it recommended.

## Context
A commit that looks like it finishes a task is evidence the work was written, not evidence
it holds up. The old default closed the entry the moment such a commit landed, so the
looser of the two readings was what an unconfigured project got, and the safer one had to
be found in the settings table. Recording the commit was never the thing at issue —
`statusSyncBlock` already records the commit and its touched files under either setting,
so the default only decides whether the close waits for a human word.

## Alternatives rejected
- Leaving the default off and relying on `foreman:init` to ask — init runs once, and a
  project that adopts Foreman by dropping a `ROADMAP.jsonl` in place never sees the
  question at all.
- Keeping a corrupt config on the old `false` reading — an unparseable file is not a
  project opting out, and reading it as one hands the loose behavior to exactly the
  projects whose config is broken.
- Adding a third mode between the two — the setting answers one yes/no question, and a
  middle value would have no behavior of its own to name.

## Consequences
Any project that never set the key sees a confirmation step it did not see before; the
README row and the changelog entry are where that is announced, and a single `false`
restores the old flow. The `post_commit.test.js` cases that pinned the absent-config and
malformed-config paths to the off behavior now pin them to on, and a new case pins the
explicit `false` opt-out — so the opt-out is covered by a test rather than by the absence
of one.
